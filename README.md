# Kratos Project Template

A project template for creating new Kratos services with HTTP and gRPC
transports, protobuf-first APIs, Wire dependency injection, OpenAPI generation,
and a small CRUD example.

Use this repository as a starting point for a new service. The included sample
resource is only reference code for API shape, layering, code generation, and
testing. Replace it with your own domain model when creating a real project.

## Create a New Project

1. Copy or generate a repository from this template.
2. Update the Go module path:

```bash
go mod edit -module github.com/your-org/your-service
```

3. Replace existing import paths that reference this template module and update
   the `module=` options in `buf.gen.yaml` to match.
4. Rename the command, service metadata, and sample API package to match your
   service.
5. Replace the sample CRUD resource with your own resource.
6. Regenerate code and verify the project:

```bash
task all
go test ./...
```

## What Is Included

- Kratos HTTP and gRPC server setup.
- Protobuf API definitions and generated Go code.
- OpenAPI generation.
- Wire-based dependency injection.
- Layered `service`, `biz`, and `data` packages.
- An Ent-backed SQL repository for the sample resource.
- Unit tests for the service layer.
- Server-streaming and bidirectional-streaming examples.

## Project Layout

```text
services/             Per-service APIs and generated bindings
services/todo/biz/    Domain models, usecases, and repository interfaces
services/todo/data/   Repository implementations and shared storage clients
services/todo/data/ent/ Ent-generated persistence models and database client
                       (handwritten schemas in data/ent/schema/)
internal/ent_schema/  Shared BaseModel with UUID ID and audit timestamp mixins
cmd/                  Application entrypoints
configs/              Local configuration
internal/server/      HTTP and gRPC server construction
internal/service/     Transport-facing service methods
internal/biz/         Usecases, entities, errors, repository interfaces
internal/data/        Repository implementations
third_party/          Protobuf dependencies
doc/swagger/          Generated OpenAPI document
```

## API Template Practices

The sample CRUD API demonstrates common conventions for Kratos projects:

- Resource-oriented methods: create, get, list, update, delete.
- HTTP annotations with `google.api.http`.
- Required fields with `google.api.field_behavior`.
- List requests with `page_size`, `page_token`, `filter`, and `order_by`.
- Pagination with `go.einride.tech/aip/pagination`.
- Partial updates with `google.protobuf.FieldMask` and `fieldmask.Update`.
- Streaming RPC definitions for one-way and bidirectional streams.

The data layer translates domain models to and from the generated `data/ent`
package and applies parsed filters and ordering through Ent. Persistence models
stay behind the repository interface; `biz` and `service` do not import them.

## Development Commands

Install [Task](https://taskfile.dev/installation/) and ensure `$(go env GOPATH)/bin`
is on your `PATH`:

```bash
go install github.com/go-task/task/v3/cmd/task@latest
```

List available commands with `task` or `task help`.

Install generators:

```bash
task init
```

Regenerate API bindings and OpenAPI:

```bash
task api
```

Buf generates service APIs and shared protos from the workspace, excluding
`internal/conf/` (generated by `task config`). Go bindings are written to the
directories declared by each proto's `go_package`, relative to the Go module.
The combined OpenAPI document is generated at
`doc/swagger/openapi.yaml`. New service API directories are discovered automatically.

Proto imports are relative to the Buf module roots (`services/` and `internal/`),
not the importing file. For example, `services/todo/api/v1/admin/todo.proto` uses:

```proto
import "todo/api/share.proto";
import "share_proto/share.proto";
```

The shared files declare distinct protobuf packages (`todo.share` and `share`).
Refer to their types as `.todo.share.TODO` and `.share.Empty`; every shared proto
also needs a `syntax`, `package`, and `go_package` declaration.

Regenerate config protobufs:

```bash
task config
```

Run Go generators (including Wire) and module cleanup:

```bash
task generate
```

Ent schema definitions live in `services/todo/data/ent/schema/` and embed the
service-local base schema instead of repeating the namespace and ID/time mixins:

```go
type Todo struct {
    baseModel
}
```

`schema/base.go` sets the PostgreSQL namespace to `todo` once for the service.
It embeds the shared `ent_schema.BaseModel` for UUIDs and audit timestamps, then
adds an `entsql.Schema("todo")` mixin. Every new model should embed `baseModel`.
The Todo model overrides only its table name to `todo`, producing `todo.todo`;
its native enum type is `todo.todo_status`.

Ent's `sql/schemaconfig` generation feature makes the client qualify SQL names
automatically, so repositories need no prefixes and do not depend on a session
`search_path`. Runtime overrides, if needed, belong at client construction in
`data` via `ent.AlternateSchema`; the schema definitions remain the defaults.

The generator writes `ent.Todo`, CRUD builders, and the database client to
`services/todo/data/ent/`. To regenerate only Ent:

```bash
go generate ./services/todo/data/ent
```

Run all generation steps, Wire, and module cleanup:

```bash
task all
```

Build:

```bash
task build
```

Test:

```bash
go test ./...
```

## Run Locally

Apply the PostgreSQL migrations before starting the app (requires the
[Atlas CLI](https://atlasgo.io/getting-started#installation)):

```bash
export DATABASE_SOURCE='postgres://postgres:postgres@127.0.0.1:5432/test?sslmode=disable'
task migrate:apply
```

`services/todo/migrations/` starts with a fresh-database migration that creates
the `todo` schema, the `todo.todo_status` native enum, and the `todo.todo` table.
It is not an upgrade migration for an existing deployment. Commit SQL migrations
and `atlas.sum` together. Startup `auto_migrate` is disabled by default: Ent does
not create native PostgreSQL enum types, so SQL migrations must run first.

Domain and persistence enum values are strings matching protobuf enum names.
Protobuf keeps numeric wire values (for compatibility) and uses the names in
JSON. Service conversions use generated name lookup maps, not switches.
Empty/unspecified values are not valid database statuses. When adding an enum
value, add its SQL migration as well as its domain/proto declarations; do not
rewrite an already-applied migration. Automatic native-enum diff generation
requires additional Atlas composite-schema setup (a Pro feature); the checked-in
SQL migrations can be applied without that feature.

```bash
go run ./cmd/app -conf ./configs
```

Optional PostgreSQL integration tests create isolated temporary databases and
verify native enum storage and schema-qualified queries, including isolation
from a same-named `public.todo` table. The test user needs `CREATEDB` permission:

```bash
TEST_DATABASE_SOURCE="$DATABASE_SOURCE" go test ./services/todo/data -run Postgres
```

Default local ports are configured in `configs/config.yaml`:

- HTTP: `0.0.0.0:8000`
- gRPC: `0.0.0.0:9000`
